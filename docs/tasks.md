## Phase 6 — Performance foundation

Goal: Fjord has a measurable performance architecture — published SLOs, realistic torture fixtures, end-to-end latency attribution, long-lived repository state, generation-scoped invalidation, snapshot-first switching, and bounded transport — rather than a subjective impression of speed. Spec: [`specs/performance.md`](specs/performance.md).

Ordered by dependency: measurement before fixtures, fixtures before budgets, budgets before architecture changes, architecture before gates.

- [x] **P6-01** — Ratify the SLO catalogue and measurement methodology (spec §1). Sixteen SLOs, each with a scenario identifier (the name `fjord-bench` emits, so budget/measurement/CI result can be joined), the fixture it runs against, and either a measured anchor or an explicit *provisional* marker — ten of sixteen were initially provisional. Measurement rules are stated per class, including P95 over ≥20 repetitions, the report-then-gate rule, and the refusal to compare across platforms. The existing checkpoints in [`benchmarks/p4-18-release.md`](benchmarks/p4-18-release.md) are absorbed as anchors rather than contradicted; P6-18 later audited every marker.
- [x] **P6-02** — `fjord-bench`: fixture manifests and reuse. Each generated fixture writes `.fjord-bench-manifest.json` with its parameters and schema version, written last so an interrupted generation regenerates; reuse requires an exact parameter match, changed parameters regenerate, `--force` regenerates unconditionally, and a non-empty directory that is not ours is refused under either flag setting (spec §2). ## Phase 10 — Daily-driver integration, advanced workflows & workspace

Goal: close the remaining daily-driver gaps — starting a branch merge, acting on a file in Working Changes, and managing stashes as first-class objects — and then turn the workspace-first architecture into the competitive advantage: worktrees, rebase, remote management, and a health model that answers "which repositories need me, and why" across dozens of repositories. Specs: [`specs/branch-merge.md`](specs/branch-merge.md), [`specs/working-tree-and-diff.md`](specs/working-tree-and-diff.md) §6, [`specs/stash-management.md`](specs/stash-management.md), [`specs/workspace-workflows.md`](specs/workspace-workflows.md).

### Phase 10 execution order

The existing stable IDs (`P10-01`–`P10-11`) are **unchanged**; they were assigned
in spec order, not in priority order. The order below is the dependency and
priority order the phase is actually worked in, expressed as notes rather than by
renumbering anything.

```text
1. P10-MERGE-01…03   Merge a branch into the current branch          ✅ done
2. P10-WC-01…06      Working Changes file context actions            ✅ done
3. P10-WC-MULTI-01   Working Changes multi-selection model
4. P10-STASH-01      Stable stash identity + the reads built on it
5. P10-STASH-02      Exact-scope stash creation                         ✅ done
6. P10-WC-MULTI-02   Batch Stage/Unstage + Stash N files… entry point
7. P10-STASH-03…06   Stash tree, inspector, graph markers, actions
8. P10-WC-MULTI-03   Batch Discard + multi-file patch export
9. P10-08/09/10      Workspace health, expected branch, filter chips
10. P10-06/07        Remote CRUD completion
11. P10-04/05        Basic rebase
12. P10-01/02/03     Worktrees
13. P10-11           Interactive rebase
```

The Stash and multi-selection blocks interleave rather than queue, because they
share exactly one edge in each direction and nothing else: `Stash N files…`
(`P10-WC-MULTI-02`) needs the exact-scope backend from `P10-STASH-02`, and
`P10-STASH-02` needs nothing from the selection work — a one-path `Paths` scope
is the same contract `Stash file…` now uses. `P10-WC-MULTI-01` leads the
whole sequence because it is pure frontend, blocks nothing, and is what every
later batch action reads from.

**`P10-STASH-02` is complete and its proof gate passed.** The gate existed
because direct pathspec stash proved only preservation of unrelated current
state, not exact later Apply/Pop behavior. It is marked done because both
invariant A and invariant B now pass against real Git, the exact-scope result
remains an ordinary Git-compatible stash, and `create_stash` with `scope: Paths`
delivers an exact subset — "Stash 4 files" means those four files both at
creation and on later use. The implementation uses explicit tree construction,
`write-tree`/`commit-tree`, and atomic `update-ref` publication with expected-OID
CAS validation ([`specs/stash-management.md`](specs/stash-management.md) §2).

Why merge is first, explicitly:

- **Merge is more fundamental daily-driver functionality than interactive
  rebase.** Fjord can already *finish* a merge — detect the state, list conflicts,
  hand off to the merge tool, continue, abort — but cannot *start* one. Merging a
  branch into the branch you are on is a routine several-times-a-week action;
  interactive rebase is a specialist tool used occasionally. A user who has to
  open a terminal to run `git merge` will finish the whole task there.
- Merge is also the cheapest of the three integration workflows to make safe: it
  reuses the Phase 9 operation state, banner, and abort path unchanged, and it
  defines the shared integration preflight that `P10-05` (rebase) then reuses
  instead of inventing.
- **Working-file context actions are workflow polish, but they materially affect
  everyday usability.** Nothing in them is a new Git capability the app lacks
  conceptually; they remove a dozen small reasons per session to leave the window
  (open this file, reveal it, ignore this generated artifact, copy this path,
  export this patch, delete this file). They are second because they are
  independent of every other Phase 10 task and can ship incrementally.
- **Stash Management is third because it is the last daily-driver gap, and it is
  built entirely from parts that now exist.** After `P10-WC-05` the app can stash
  one file with a proven unrelated-current-changes invariant, and after
  `P10-MERGE-01`–`03`
  it can stash before an integration — but it still cannot *see* a stash, act on
  anything but `stash@{0}`, or get stashed work back onto a branch of its own.
  Every piece it needs is shipped: the exact-scope stash engine, the destructive
  preflight/token path, the RepoTree section pattern, the commit-graph ref-badge
  row, the Commit Inspector composition, the bounded diff pipeline, and the
  generation model. It comes before Workspace Intelligence because it removes a
  reason to open a terminal on a single repository, which is the higher-frequency
  need. Spec: [`specs/stash-management.md`](specs/stash-management.md).

- [x] **P10-STASH-02** — Unified stash creation for all / one / many paths with a
  user-authored name, and an **exact** scope contract. One typed contract
  `CreateStashRequest { scope: All | Paths { paths }, message, include_untracked }`;
  an empty `paths` is `stash_scope_empty`, **not** a spelling of `All` (the
  `stage_files` "empty means all" convention is deliberately not extended to a
  command that removes work from the working tree — spec §2.1). The two scopes are
  **two different contracts** (spec §2.1): `All` keeps conventional
  whole-repository semantics, while `Paths` is an exact semantic subset — it
  defines the entry's reusable contents, not merely which files leave the current
  working tree. **This task must prove two invariants, not one** (spec §2.3):
  **(A)** creating the stash leaves every unrelated staged, unstaged, and
  untracked change byte-for-byte unchanged — `P10-WC-05`'s invariant, restated for
  *n* paths; and **(B)** a later Apply / Pop of that entry touches **only** the
  selected paths, i.e. `set(touched) == set(requested)`. Historically,
  `P10-WC-05` proved (A) only: verified against real Git, a pathspec-scoped
  `git stash push` records whole trees, so unrelated staged content lands in the
  entry and is reapplied (spec §4.3). **Direct pathspec
  `git stash push -- <paths>` was therefore insufficient** for the final
  contract. `Paths` was treated as a **construction** problem (spec §2.2), and
  the completed implementation uses private indexes, `write-tree`/`commit-tree`,
  and atomic `update-ref` CAS publication.
  The result must stay an ordinary Git stash — `git stash list`/`show`/`apply`/`pop`
  must work on it from a terminal. Explicitly forbidden: a Fjord stash database, a
  patch file posing as a stash, temporary mutation of unrelated working files, and
  any "hide → stash → restore" sequence with no atomic boundary. **Completed
  proof gate:** the task was eligible to close only after apply-side fixtures
  proved both invariants against real Git and ordinary Git compatibility. Had
  that proof failed, the historical acceptance rule was to leave the task open
  and withhold `Stash N files…`, because a smaller safe product is better than a
  `Stash 4 files` that restores five. The proof passed. A selection whose state
  the construction cannot represent exactly fails closed with
  `stash_scope_unrepresentable` and
  creates nothing. One engine and one module: `stash.rs` owns the private-index /
  `write-tree` / `commit-tree` construction, real `index.lock` plus prepared
  expected-HEAD validation, and reflog-creating `update-ref` CAS publication;
  `git2::stash_save2` is retired, `stash_push`/`stash_file` collapsed
  into `create_stash`, and **`Stash file…` was migrated onto the new engine** so
  one-file and *n*-file stashes cannot end up with different apply semantics
  (spec §2.9) — there is one implementation of interactive scoped
  stash. Everything runs through the resolved `GitCommandFactory` with
  individually passed arguments, under the repository write lock. Git ≥ 2.23 gates

### Working Changes multi-selection and batch actions

Spec: [`specs/working-tree-and-diff.md`](specs/working-tree-and-diff.md) §7 — the
single owner of the Working Changes selection model and of every batch action
built on it. Multi-file **stash** semantics stay in
[`specs/stash-management.md`](specs/stash-management.md) §2; this block owns only
the selection and the entry point that passes it.

Why this is its own block rather than part of Stash Management: the same
selection feeds Stage, Unstage, Discard, patch export, and stash. Four of those
five have nothing to do with stash, so putting the model in the stash spec would
have made them all depend on it. **The previously drafted `P10-STASH-07` is
withdrawn** and replaced by `P10-WC-MULTI-01`–`03`; no other stash task changes,
and no ID is renumbered.

Dependency order — `P10-WC-MULTI-01` → `02` → `03`, with one cross-edge:
`P10-WC-MULTI-02`'s `Stash N files…` entry point additionally requires
`P10-STASH-02`'s exact-scope backend and its passed proof gate, so the
recommended interleaving is
`WC-MULTI-01` → `STASH-01` → `STASH-02` → `WC-MULTI-02` → `STASH-03…06` →
`WC-MULTI-03`. `P10-WC-MULTI-01` is deliberately first in the whole sequence: it
is pure frontend, unblocks nothing else, and is the piece every later batch
action reads from.

- [x] **P10-WC-MULTI-01** — The selection model and desktop selection semantics, frontend only (spec §7.3–§7.9). `FileEntryList`'s `selectedPath: string | null` becomes `selectedPaths: ReadonlySet<string>` + `activePath`, scoped to the one section it renders, and its `onSelect` grows `{ toggle, range }` modifier flags; it gains **no** Git semantics, no source awareness, and no action knowledge — the panel maps its section's paths onto the shipped `WorkingFileTarget { path, source }` and the application layer owns the rest, holding the `P10-WC-01` boundary one level further out. Selection state is `{ targets: Set<WorkingFileTarget>, active, anchor }`, keyed by **path + source** and never by row index, virtual item, positional React key, or `HTMLElement` — `FileEntryList` virtualizes and recycles rows, so any of those silently becomes a different file on scroll. Gestures: click selects one; `Ctrl`/`Cmd`+Click toggles; `Shift`+Click ranges inclusively from a stable anchor **in current display order**; `Ctrl`/`Cmd`+`Shift`+Click adds a range; arrows move `active` and collapse, `Shift`+arrows extend, `Ctrl`/`Cmd`+`Space` toggles in place, `Escape` collapses. In Tree view the range spans **visible** rows, skips directory rows, and never reaches into a collapsed directory — selecting what is not on screen is how a batch discard removes work the user never saw. Directory rows are never selectable. `Ctrl`/`Cmd`+`A` selects every visible file row in the **focused section only**. **Cross-section selection is impossible by construction** (§7.5): touching a row in the other section clears and restarts, because Stage applies to worktree rows, Unstage to index rows, Discard only to `INDEX -> WORKTREE`, and a patch has exactly one side — every mixed case would resolve to a disabled action whose honest reason is "this cannot apply to what you selected". **Right-click is a behavioral fix to shipped code**: `FileRow` today calls `onSelect(file)` unconditionally in both its `onContextMenu` and its `Shift+F10`/Context-Menu-key handler, so a user who `Ctrl`-clicks four files loses three of them the instant they right-click to act — it becomes preserve-if-inside, replace-if-outside, on both input paths. Accessibility: each section's list becomes `role="listbox"` + `aria-multiselectable`, rows `role="option"` + `aria-selected` (today they are `<button>`s with only a `data-selected` attribute), one roving `tabindex` follows `active`, focus stays separate from selection, and the `N selected` count is announced through the existing polite live region. Selection is frontend-only: toggling runs no query and no IPC, toggle is O(1), and deriving a dispatch payload is O(selected). Verification: spec §7 frontend cases 1–6, 10–16.
- [x] **P10-WC-MULTI-02** — Batch **Stage** / **Unstage**, the selection-aware **Stash** entry point, and the selection toolbar (spec §7.10–§7.11, §7.14). One shared selection-action model drives the context menu and section strip, sends one canonical non-empty path vector per Stage/Unstage action, refuses mixed/stale/conflicted selections at dispatch, and follows successful work across the next authoritative Working Changes result in both directions. `Stash N files…` opens the shipped `CreateStashDialog` with `StashScope::Paths` and uses the existing `create_stash` command and Git >= 2.23 fail-closed capability gate; no stash API or dialog was added. The required libgit2 fixture reproduced pathspec globbing (`report[1].txt` also matched `report1.txt`), so explicit Stage now uses literal `add_path`/`remove_path` operations and explicit Unstage restores exact HEAD entries inside one fresh-index transaction and one write; empty-list all-files semantics remain unchanged. Counted labels and toolbar accessibility ship in all five locales. - [x] **P10-WC-MULTI-03** — Batch **Discard** and multi-file **patch export** (spec §7.12–§7.13). Batch discard gets a batch *contract*, never a loop: three confirmed single-file discards in sequence produce exactly the partial-success state the safety model exists to prevent — one confirmed sentence, one to three files changed depending on where it failed. `PatchSelection` stays per-file (it is the right granularity and every shipped validator depends on it); the batch is an ordered vector of them plus one new `DestructiveAction::DiscardFiles { paths }` on the **existing** enum, executed by a new `discard_patches { selections: Vec<PatchSelection>, … }` — whole-file only, since hunk and line discard have no multi-file UI that could produce them and no sentence that could describe them honestly. Atomicity is **Git's own**, not something Fjord layers on: the batch runs `discard_patch`'s existing sequence *once* — one write lock, one token, one `index.lock`, one rebuild, one `git apply --reverse --check` over the concatenated patch, one re-verification, one apply, one `MutationKind::Discard` bump — and `git apply` validates every hunk of every file before touching the worktree. One preflight dialog bound to the whole set aggregates the shipped per-file consequence computation into a bounded file sample and exact summed line count, so **no new consequence variant is needed**; the token binds repository, action, every selection in order, every `base_digest`, and the `GenerationSet`. **Staleness is all-or-nothing**: if any selected file changed after preflight the whole batch fails `patch_stale`/`preflight_stale` and nothing is discarded — the remaining files are not "still fine", because a subset is not what the user confirmed. A partially staged path's unstaged row discards `INDEX -> WORKTREE` only and leaves its staged side byte-identical, exactly as single-file discard already does, which is why the selection carries `source` rather than a bare path. Nothing is ever silently skipped: a conflicted member refuses the batch, and an unsupported binary/mode-only member makes the complete patch action fail `patch_unsupported`; the lightweight row model names an offending path only where it has that availability data. Patch export becomes multi-file by widening the shipped commands rather than adding a second pair: `export_patch` and `get_patch_text` take `selections: Vec<PatchSelection>`, a single file being a vector of length one. Output is **one** valid `git apply`-able unified patch — unstaged selection → combined `INDEX -> WORKTREE`, staged → combined `HEAD -> INDEX` with `--cached`; a mixed-source request is refused backend-side even though §7.5 prevents it in normal UI selection. Each file's section comes from the shipped `P8-01` `build_unified_patch` unchanged, digest-verified before its bytes are emitted, then concatenated in **byte-lexicographic repository-path order** — Git's own diff ordering — so two exports of one selection are byte-identical and click order never leaks into the file. Both commands stay read-only: read lock, no index lock, no generation bump. Default filename `<repository-name>-<n>-files.patch`; `Copy patch for N files` is the same bytes through the clipboard from the identical builder. Verification: spec §7 backend cases 24–32, including the stale-one-refuse-all case, the partially-staged index preservation, cross-set token binding, both apply round-trips, the no-unselected-path assertion, and ordering determinism.
