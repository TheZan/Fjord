# Spec: internationalization

Referenced by: P0-07, and every feature PR that adds user-facing text from Phase 1 onward.

## File layout

```
locales/
  registry.ts          # supported locale codes + display names, single source of truth
  en/
    common.json         # buttons, generic labels, error codes
    workspace.json       # workspace/dashboard screen
    repo.json             # single-repo view: branches, commits, diffs
    settings.json
    glossary.md           # not loaded at runtime — reference doc for translators
  ru/
    common.json
    workspace.json
    repo.json
    settings.json
```

One namespace file per feature area, not one giant catalog — a PR that touches the repo view only ever diffs `repo.json` in each locale, which is what makes the CI key-diff check (below) actually readable instead of a wall of noise.

## Adding a locale

1. Copy `locales/en/*.json` to `locales/<code>/*.json`, translate values (keys never change).
2. Add one entry to `locales/registry.ts`: `{ code: '<code>', label: '<Native name>' }`.
3. Done — no component touches a locale code directly; the locale switcher renders off the registry, and `react-i18next` picks up the new namespace files automatically.

This is the mechanism behind SDD §6.2's "a new locale is a content-only change" — if step 3 above ever needs a code change to make a new locale appear in the switcher, that's a bug in the registry wiring, not an expected part of adding a language.

## Key naming

`feature.section.key`, e.g. `workspace.dashboard.needAttention`, `repo.commitGraph.loadEarlier`. Namespace (the JSON filename) already scopes `feature`; the dotted key inside it groups by UI section so a translator can find "which screen is this on" without reading component code.

## The glossary — preserving technical terms

`locales/en/glossary.md` (English-authored, referenced by all translators) lists Git and product vocabulary with a fixed treatment per locale:

| Term | Russian |
|---|---|
| commit | коммит |
| branch | ветка |
| merge | слияние |
| rebase | rebase *(kept in Latin — no natural Russian git-community equivalent)* |
| stash | stash *(kept in Latin)* |
| pull / fetch / push | kept in Latin — these are also literal command names elsewhere in the UI |
| workspace | рабочее пространство |

This table is authoritative — a translation PR that renders `rebase` as a Cyrillic transliteration is a review comment, not a style preference.

Where a term must sit *inside* a translated sentence, it's passed as an i18next interpolation variable, never typed directly into the translated string:

```json
// workspace.json (en)
{ "mergedInto": "Merged into {{branch}}" }
// workspace.json (ru)
{ "mergedInto": "Слито в {{branch}}" }
```

```ts
t('workspace:mergedInto', { branch: 'main' })
```

`{{branch}}` is substituted verbatim after translation — a branch name, SHA, or file path is never something a translator can accidentally mangle, because it's never inside the string they're translating.

## Fallback chain

Selected locale → English → raw key (visibly broken, intentionally — a raw key in the UI is a loud bug, not a silent one).

## CI check

A script (`scripts/check-i18n.ts`, run in CI) loads every `locales/<code>/*.json`, diffs its key set against the matching `locales/en/*.json` file, and fails the build on any missing or orphaned key, per namespace, per locale. This is what makes "translation drift" a build failure at PR time instead of a bug report from a Russian-locale user weeks later.
